# 02: Pattern Library and Concept Use

## Stage goal

Turn a growing stream of single-asset, single-axis classifications into an actual
usable library, and close the loop by feeding it into the existing ideation engine,
rather than building a second, separate concept generator.

This stage is modeled on the account's existing Voice of Customer Audit process:
extract recurring structure rather than one-off color, and never present a thin,
single-example pattern as proven.

## Step 1: Check the new entry against what's already there

Every time a new asset is classified into an axis, check whether it matches an
existing entry (seeded per `01` Step 0, or confirmed from an earlier submission) or is
a genuinely new bucket:

- If it matches an existing entry, add it as a new supporting example under that
  entry, with its own verbatim, visual, evidence trail, and taste note.
- If it's a proposed new bucket, it starts as a single-example candidate, flagged as
  such, not treated as a proven pattern yet.

## Step 2: For video assets, extract the beats too

For video assets, once the identified axis is classified, capture the fuller
structure around it for context, since that's what makes the entry useful later:

1. **Hook**
2. **Tension / problem statement**
3. **Personal stake or proof**
4. **Turn / resolution** (usually where a creative mechanic lives)
5. **Payoff / CTA**

This doesn't turn a single-axis submission into a three-axis classification, the
identified axis from `01` is still the one thing formally banked, but the surrounding
beats make the entry more useful on review. Static images skip this step.

## Step 3: Roll up recurring shapes within an axis

Within each axis's library, look for repeated shapes across multiple submitted
assets. A shape only earns its own confirmed library entry once it shows up
independently more than once; a single strong example stays a flagged candidate.

Each confirmed entry carries: a short name, its axis, how often it recurred, the
verbatim + visual + evidence for every supporting example, and the personal taste
notes that came with each one, since taste is the actual signal this library is built
from.

## Step 4: Confirmation gate

Same gate as `05-library-confirmation.md`. A proposed entry is a candidate until a person signs off on
it. Always disclose how many examples actually back it so nobody treats a thin
pattern as a strong one.

## Step 5: Use the library, don't rebuild concept generation

Once entries are confirmed, the closing move is a direct prompt into the **existing
ideation engine and concept-output flow already built for this account**, using the
new library as an additional input bank, exactly like the messaging angle, visual
format, hook, and mechanic banks it already draws from:

> "Based on what I've saved, give me a new hook using this pattern for [product]."

> "Look through my library and find something I haven't done yet for [product]."

This package does not duplicate that concept-assembly logic. It produces the input;
the existing engine does the assembly.

## Step 6: Mark it tested once it's actually run

`new-angles-to-test.md` (see `01`, "The library's structure") only means anything if
it stays accurate. When a person confirms an ad actually launched using a pattern from
that list, remove its row (or mark it tested with the launch date, whichever this
account prefers), so the list only ever shows what's genuinely still untried. Being
pulled into a concept suggestion is not the same as being tested, only a real launch
clears a row.

## What this is for

The finished library answers a specific, practical question: "if I want a new hook,
format, or script that sounds like something I already believe is good, not a guess
at what's on-trend, which pattern do I follow, and what does it actually look like in
someone else's real words?" It's a reference for the existing ideation engine to pull
from, not a second engine.
